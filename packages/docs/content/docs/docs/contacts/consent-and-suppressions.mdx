## SMS consent

`contacts.sms_consent` is false by default and can only be set with an `admin`-scoped key (`PUT /v1/contacts/{id}/sms-consent`, with `source` and `at` for your records). No text leaves for a contact without it: the SMS executor skips the step with `no_consent`, and the `contact.sms_consent` fact is there for conditions that route non-consenting contacts elsewhere. The other SMS gates, also not configurable: a phone, a country in `settings.sms_countries` (default `["US"]`), a known recipient time zone, and 08:00 to 21:00 in it.

## Suppressions

A suppression is a mark on a contact for one channel (`email`, `sms`) or `all`, with a reason. It is checked **at enrollment** (`all` suppressions exclude the contact from the batch with `suppressed:<reason>`) and **again at execution** (an email step skips with `suppressed` when the contact is suppressed on `email` or `all`; the same for SMS). `GET /v1/contacts/{id}` lists them.

| Source | Channel | Reason | Also |
|---|---|---|---|
| The opt-out link in an email (`{{ unsubscribe_url }}`, `List-Unsubscribe` headers), on the hosted page or through `POST /v1/unsubscribes/{token}` | `email` | `opt_out` | exits the enrollment with `opt_out` |
| A `STOP` text (`STOP`, `QUIT`, `END`, `CANCEL`, `UNSUBSCRIBE`, `OPT OUT`, `STOPALL`) | `sms` | `opt_out` | exits |
| A hard bounce | `email` | `hard_bounce` | exits with `bounced`; a soft bounce suppresses nothing |
| A complaint | `email` | `complaint` | exits with `bounced` |
| Your report `{ type: "opt_out", channel }` (`channel` defaults to `all`) | the channel | `opt_out` | exits |
| Your report `{ type: "suppressed", reason }` | `all` | your reason (`do_not_contact`, `bad_number`, `invalid_email`, `left_company`, …) | exits with `suppressed` |

Suppressions are never removed by the API today; erase the contact and create it again if a suppression was wrong.

## The opt-out link

Every email body should contain `{{ unsubscribe_url }}` (publishing without it is the warning `NO_UNSUBSCRIBE`). It renders a signed link valid for 90 days. Every email also carries `List-Unsubscribe: <url>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` headers with the same URL, so mail clients show their own unsubscribe button. The token is derived from `SEQ_ENCRYPTION_KEYS`; rotating the first key invalidates links already sent.

Without the project setting `unsubscribe_url`, the link points at a page this server hosts, `SEQ_PUBLIC_URL/u/{token}`. It shows a one-click page; the click, or the one-click POST that mail clients send, writes the `email` suppression and exits the enrollment. This is enough for a self-hosted install with no app in front of it.

## Host the unsubscribe page in your app

When OpenSequence runs behind your product, the link should be on your domain, and your app should show the page. OpenSequence only answers your API calls.

First, set the project's `unsubscribe_url`: an `https` URL containing `{token}`, where the signed token goes. With an `admin` key:

```bash
curl -X PUT $SEQ/v1/project/settings -H "Authorization: Bearer $ADMIN_KEY" -H "Content-Type: application/json" \
  -d '{"unsubscribe_url":"https://app.example.com/u/{token}"}'
```

```ts
await oseq.project.updateSettings({ unsubscribe_url: 'https://app.example.com/u/{token}' });
```

From then on `{{ unsubscribe_url }}` and both headers render `https://app.example.com/u/<token>`. A URL that is not `https`, or has no `{token}`, is refused with `INVALID_SETTINGS`. Set it to `null` to go back to the hosted page.

Then, on GET of that page, read the token with an `enroll` key and show a confirmation. Reading changes nothing. The email is masked so a forwarded link does not reveal the address:

```ts
const status = await oseq.unsubscribes.get(token);
// { valid: true, expired: false, contact: { email: 'd***@acme.com', first_name: 'Dana' }, already_unsubscribed: false }
```

An unknown, altered or other-project token reads `valid: false`; an expired one reads `valid: false, expired: true`.

When the person confirms, apply it:

```ts
await oseq.unsubscribes.apply(token); // POST /v1/unsubscribes/{token}
```

This writes the `email` suppression and exits the contact's enrollments with `opt_out`, exactly like the hosted page. It is idempotent: a second call changes nothing and returns `already_unsubscribed: true`. An invalid token is a `400` with `UNSUBSCRIBE_TOKEN_INVALID`, an expired one `UNSUBSCRIBE_TOKEN_EXPIRED`.

Finally, accept a POST on the same URL. Under RFC 8058, Gmail, Yahoo and Apple Mail unsubscribe with one click by sending `POST https://app.example.com/u/<token>` with the body `List-Unsubscribe=One-Click`, without opening the page. Your handler applies the token on that POST, answers `200` without a redirect or a login, and must not require a CSRF token for it. Bulk senders are required to support one-click unsubscribe.

## What exits, what pauses

| Signal | Effect on the contact's active enrollments |
|---|---|
| opt-out, hard bounce, complaint, suppression | **exits**, whatever the definition says |
| reply, connected call | exits when `exit_on` contains `reply`; otherwise may wake a `wait_for` |
| meeting booked | exits when `exit_on` contains `meeting_booked` |
| out-of-office auto-reply | **pauses** until the stated return date or 7 days; never exits |
| sender channel `credentials_needed` | the send that finds out is deferred an hour; from then on, email steps skip with `sender_channel_credentials_needed` until the sender reconnects |

The service only sees its own channels: replies in threads it started, bounces, STOP texts, unsubscribe clicks, out-of-office messages. Everything in your world (a meeting booked in another tool, a do-not-contact flag in the CRM, a person who left) must be [reported](/docs/contacts/events), or the service keeps emailing people your users already excluded.
