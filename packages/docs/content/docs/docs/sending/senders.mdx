A sender is the person an enrollment acts as: emails go out from their mailbox, texts from their number, tasks land in their inbox. Register a sender once with your own user id, then connect the channels they send on.

<CodeGroup>

```bash title="curl"
curl -X PUT $SEQ/v1/senders/u_42 -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d '{
  "name": "Max Rivera",
  "email": "max@acme.com",
  "timezone": "America/New_York",
  "attrs": { "title": "Account Executive" },
  "signature_html": "<p><b>Max Rivera</b><br>Account Executive, Acme<br><a href=\"https://cal.com/max\">Book a call</a></p>"
}'
```

```ts title="TypeScript"
const sender = await oseq.senders.upsert('u_42', {
  name: 'Max Rivera',
  email: 'max@acme.com',
  timezone: 'America/New_York',
  attrs: { title: 'Account Executive' },
  signature_html: '<p><b>Max Rivera</b><br>Account Executive, Acme<br><a href="https://cal.com/max">Book a call</a></p>',
});
```

</CodeGroup>

`PUT /v1/senders/{id}` creates or updates the sender (an upsert on your id). It needs an `admin` key. In every sender route, `{id}` is your own id or the service id (`snd_…`); prefix yours with `ext:` if it could look like a service id.

The sender comes back as a stored record, camelCase, with your id as `externalId`. This is the whole object, the same one `GET /v1/senders` lists and `GET /v1/senders/{id}` extends:

```json
{
  "id": "snd_01J9…",
  "projectId": "prj_01J9…",
  "externalId": "u_42",
  "name": "Max Rivera",
  "email": "max@acme.com",
  "timezone": "America/New_York",
  "status": "active",
  "attrs": { "title": "Account Executive" },
  "signatureHtml": "<p><b>Max Rivera</b><br>Account Executive, Acme<br><a href=\"https://cal.com/max\">Book a call</a></p>",
  "signatureText": "Max Rivera\nAccount Executive, Acme\nBook a call (https://cal.com/max)",
  "createdAt": "2026-10-13T09:00:00.000Z",
  "updatedAt": "2026-10-13T09:00:00.000Z"
}
```

To join the list back to your users, match `externalId` to your user id (or keep the `snd_…` id when you create the sender). `status` is `active` or `disabled`.

| Field | Notes |
|---|---|
| `name` | Required, up to 160 characters. Templates read `{{ sender.name }}` and `{{ sender.first_name }}` (the first word of the name). |
| `email` | The person's address, for `{{ sender.email }}`. The email channel's address comes from the mailbox you connect; for SMTP it is the fallback `from` when the SMTP login is not an address. |
| `timezone` | An IANA zone such as `Europe/London`, default `UTC`. Tasks are due and expire on the sender's calendar, and a send window with `tz: "sender"` follows it. |
| `attrs` | Free JSON. Templates read `{{ sender.attrs.<path> }}`. |
| `signature_html` | The email signature as HTML, up to 1 MB, so a base64 logo fits. See below. |
| `signature_text` | The plain-text signature, up to 4,000 characters. Derived from the HTML when you omit it. |

## The signature

`{{ sender.signature }}` inserts the signature into an email. In a `format: "html"` email it inserts `signature_html` as is (it is the one template value that is not escaped). In a `format: "text"` email it inserts `signature_text`.

```text
Hi {{ contact.first_name | "there" }},

…

{{ sender.signature }}
```

A signature can be as rich as the rest of a branded email: a table layout, inline styles, a logo. Any rep can edit one, and it goes into every email they send, so the HTML is sanitized when you save it with an email allowlist. A signature can never carry a script, a form or a tracking frame.

- Kept tags: `table`, `tbody`, `thead`, `tr`, `td`, `th`, `div`, `span`, `p`, `br`, `hr`, `a`, `img`, `b`, `strong`, `i`, `em`, `u`, `s`, `small`, `font`, `h1` to `h6`, `ul`, `ol`, `li`, `center`, `blockquote`.
- Kept attributes: `style`, `align`, `valign`, `width`, `height`, `bgcolor`, `border`, `cellpadding`, `cellspacing`, `alt`, `title`; `href` over `http`, `https`, `mailto` and `tel`; `src` over `https` or as `data:image/png`, `jpeg`, `gif` or `webp` with base64.
- Kept CSS in `style`: `color`, `background`, `background-color`, the `font-*` and `text-*` properties, `line-height`, `letter-spacing`, `margin*`, `padding*`, `border*`, `border-radius`, `width`, `height`, `max-width`, `min-width`, `display`, `vertical-align`.
- Removed: everything else, including scripts, event handlers, forms, iframes, `javascript:` links, images over plain `http`, and CSS with `url()`, `expression()` or `javascript:`.

A base64 logo in a signature is sent as an inline attachment, like any embedded image in an html body ([HTML emails and images](/docs/sequences/templates#html-emails-and-images)). Keep it small, a few kilobytes: it travels with every email the sender sends.

```html
<table cellpadding="0" cellspacing="0" style="border-collapse:collapse;font-family:Arial,sans-serif">
  <tr>
    <td style="padding-right:12px;border-right:2px solid #0a66c2">
      <img src="data:image/png;base64,iVBORw0KGgo..." alt="Acme" width="48" height="48" style="display:block">
    </td>
    <td style="padding-left:12px;font-size:13px;line-height:18px;color:#333333">
      <strong>Max Rivera</strong><br>Account Executive, Acme<br>
      <a href="https://cal.com/max" style="color:#0a66c2">Book a call</a>
    </td>
  </tr>
</table>
```

When you send `signature_html` without `signature_text`, the text version is rebuilt from the HTML: one line per block, links as `label (url)`, images as `[alt]`. Omit both fields to keep the stored signature; send `null` to clear one. A sender without a signature renders the template's fallback, if any: `{{ sender.signature | "Max" }}`.

## Channels

A sender sends through channels. Each one is created by its own call and has its own status and limits.

| Channel | How it is created | Page |
|---|---|---|
| `email` | `PUT /v1/senders/{id}/channels/email` with SMTP and IMAP settings | [Email via SMTP and IMAP](/docs/sending/email-smtp) |
| `sms` | `PUT /v1/senders/{id}/channels/sms` with an Allo user and number | [SMS and calls via Allo](/docs/sending/sms-and-calls-allo) |

A sender has at most one `email` channel. An `outreach` step with `channel: "email"` sends through it. Calls are not a channel: a `call` [task](/docs/sending/call-tasks) uses the sender's `sms` channel as their Allo identity. [Channels](/docs/sending/channels) compares them.

A channel's `status` is `pending`, `active`, `paused`, `credentials_needed`, `restricted` or `disconnected`. Only an `active` channel sends. A step that reaches a channel in any other status is skipped with the reason `sender_channel_<status>` and the flow moves on. A missing channel skips with `no_email_channel` or `no_sms_channel`.

### Limits

<CodeGroup>

```bash title="curl"
curl -X PATCH $SEQ/v1/senders/u_42/channels/email -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"daily_limit":50,"min_gap_seconds":90}'
```

```ts title="TypeScript"
await oseq.senders.patchChannel('u_42', 'email', { daily_limit: 50, min_gap_seconds: 90 });
```

</CodeGroup>

| Field | Default (email / sms) | Meaning |
|---|---|---|
| `daily_limit` | 30 / 100 | Sends in a rolling 24 hours. Over it, the step waits an hour and tries again, and the enrollment shows `waiting_limit`. `null` removes the cap. |
| `min_gap_seconds` | 60 / 0 | The least time between two sends on the channel. A step inside the gap waits until it ends. |
| `weekly_limit` | none | Stored, not enforced yet. |
| `opted_in` | | `true` records `opted_in_at`, the sender's own acknowledgement for the channel. Stored, not enforced. |
| `status` | | `paused` stops the channel without removing it; `active` resumes it. No other value is accepted here. |

Limits are per sender and channel, so a batch of 5,000 enrollments never fires at once. Enrolling also spreads first touches over days by the sender's email `daily_limit`: the enroll preview reports it as `capacity.per_day` and `capacity.days_to_first_touches`.

## Readiness

Before you enroll, ask which steps a sender can run, and why not.

<CodeGroup>

```bash title="curl"
curl $SEQ/v1/senders/u_42/readiness -H "Authorization: Bearer $KEY"
# {"email":{"ok":true},"sms":{"ok":false,"reason":"no_allo_number"},"task":{"ok":true}}
```

```ts title="TypeScript"
const readiness = await oseq.senders.readiness('u_42');
if (!readiness.email.ok) console.log(readiness.email.reason); // no_email_channel, email_credentials_needed, …
```

</CodeGroup>

| Reason | Meaning |
|---|---|
| `no_email_channel` | The sender has no mailbox connected yet. |
| `no_allo_number` | The sender has no sms channel. |
| `<channel>_<status>` | The channel exists but is not active, for example `email_credentials_needed` or `sms_paused`. |

`task` is always `ok`: any sender can be given a manual step. `GET /v1/senders/{id}` returns the sender with its `channels`, `readiness` and `connections` (the mailbox, never a secret) in one call.

## Listing

`GET /v1/senders` is cursor-paginated (`limit`, `cursor`, `updated_since`) and needs a `read` key. `GET /v1/senders/{id}/tasks` lists the sender's tasks, open ones by default ([Call tasks and the task inbox](/docs/sending/call-tasks)).

## Disabling a sender

<CodeGroup>

```bash title="curl"
curl -X DELETE $SEQ/v1/senders/u_42 -H "Authorization: Bearer $KEY"
```

```ts title="TypeScript"
await oseq.senders.disable('u_42');
```

</CodeGroup>

`DELETE /v1/senders/{id}` disables the sender; nothing is deleted. New enrollments as this sender are refused with `409 SENDER_DISABLED`. Enrollments already running keep going on the sender's channels while those channels are active, so pause the channels too if the person has left.

<Warning>There is no way to re-enable a disabled sender through the API yet: a later `PUT` updates the profile but keeps the `disabled` status.</Warning>

To remove one channel instead, `DELETE /v1/senders/{id}/channels/sms` or `/channels/email` deletes it, and its steps skip from then on. Removing email also deletes the stored SMTP and IMAP passwords.
