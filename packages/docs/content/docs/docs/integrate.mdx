title: "Integrate OpenSequence into your product"
description: "The recipe for adding OpenSequence to an existing app: the questions to settle first, every API call in order, the events to handle, and the admin screens to build."
---

OpenSequence is headless. It schedules and sends multi-step outreach (email, SMS, call tasks) from your users' own mailboxes and numbers, and it ships **no UI**: your product keeps its people, its reps, its screens and its design system, talks to the service over a small HTTP API, and hears back through signed webhooks. This page is the whole integration in order, for an engineer or an agent given the prompt "add OpenSequence to my code". Every step names the endpoint, the SDK method and the page with the detail.

The TypeScript SDK (`@opensequence/sdk`) is not on npm yet. Every call below is shown as the raw request too; see [TypeScript SDK](/sdks/typescript) for how to build the package or use a 15-line `fetch` helper instead.

## Ask these first

Settle these with the owner of the product before writing code. Each one decides a step below.

| Question | Why it matters |
|---|---|
| **Where is the service and what is the project key?** The base URL (`SEQ_PUBLIC_URL`, for example `https://sequences.example.com`) and an API key `sk_live_…` with the `admin` scope. If there is no instance yet, [install one](/docs/self-hosting/install) first; the operator creates the project and the first key with `POST /v1/admin/projects`. | Every request needs both. Configuration (senders, sequences, webhooks) needs `admin`; the code path that enrolls on a user's click can use a narrower `enroll` key. |
| **Which table holds the people you reach out to, and which holds the reps who send?** | People become **contacts** keyed by your record id; reps become **senders** keyed by your user id. Your ids are the join key everywhere, so nothing needs a mapping table. |
| **Which channels: email, SMS, call tasks?** | Email needs each rep's mailbox over SMTP and IMAP. SMS and calls need an Allo account and a number per rep. Call tasks need nothing but somewhere in your UI to show them. |
| **Which countries may receive texts?** | Texts to a contact outside `settings.sms_countries` are skipped, not sent (default `["US"]`). Consent is off by default and must be recorded per contact. |
| **Where should replies and events show up in your app?** An activity feed, a timeline on the person's record, a notification, a CRM field. | This is what your webhook handler writes. Decide the target per event kind before you build it. |
| **Which mailbox provider do the reps use: Google Workspace, Microsoft 365, or other?** | Google Workspace and Gmail connect with an app password. Any other mailbox with SMTP and IMAP password login connects too. Microsoft 365 and Outlook.com **cannot** connect: Microsoft retired password sign-in. Say so before promising email. |
| **Do you have a design system?** | The admin screens in the last section are yours to render. OpenSequence returns data, never markup. |

## The recipe

<Steps>

<Step title="Configure the client">

Two values: the base URL and the key. Keep the key out of the browser; every call goes from your server.

<CodeGroup>

```bash title="curl"
export SEQ=https://sequences.example.com
export KEY=sk_live_…
```

```ts title="TypeScript"
import { OpenSequence } from '@opensequence/sdk';
const oseq = new OpenSequence({ baseUrl: process.env.SEQ_URL!, apiKey: process.env.SEQ_KEY! });
```

</CodeGroup>

Every response is `{ success, data, meta }`; every error has a stable `code` to branch on. Request bodies are snake_case; stored records come back camelCase. Read [Conventions](/api/conventions) once; it is short and it is the same on every endpoint.

</Step>

<Step title="Check the service is up">

`GET /healthz` (no auth, outside `/v1`) answers `{ "ok": true }` while the process is up; `GET /readyz` answers `200` once the database is migrated and reachable. For a status panel in your app, `GET /v1/engine/health` (an `admin` key) returns the kill switches, queue depths and when each scheduler job last ran.

<CodeGroup>

```bash title="curl"
curl $SEQ/healthz
curl $SEQ/v1/engine/health -H "Authorization: Bearer $KEY"
```

```ts title="TypeScript"
const health = await oseq.project.health(); // { flags, queues: [{ queue, depth, oldestMs }], jobs, paused }
```

</CodeGroup>

</Step>

<Step title="Sync people to contacts">

One contact per person, addressed by **your** id: `PUT /v1/contacts/{your id}` creates or updates, `attrs` are merged. Up to 500 at a time with `POST /v1/contacts:batch`. Send `email` for email steps, `phone` (E.164) and `country` (ISO alpha-2) for texts, `timezone` (IANA) so sends land in the contact's day. Anything your sequences will branch on goes in `attrs`.

<CodeGroup>

```bash title="curl"
curl -X PUT $SEQ/v1/contacts/p_7 -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{ "first_name": "Dana", "last_name": "Whitfield", "email": "dana@example.com", "phone": "+14155550100", "country": "US", "timezone": "America/Los_Angeles", "attrs": { "plan": "trial" } }'
```

```ts title="TypeScript"
await oseq.contacts.upsert(person.id, { first_name: person.firstName, last_name: person.lastName, email: person.email, phone: person.phone, country: person.countryCode, timezone: person.timezone, attrs: { plan: person.plan } });
await oseq.contacts.batch(people.map((p) => ({ external_id: p.id, email: p.email, first_name: p.firstName })));
```

</CodeGroup>

The record comes back with your id as `externalId`. Call the upsert from the same place your app saves a person, so the contact never lags your database. If your ids could look like a service id (a known prefix and 26 characters), write them as `ext:<id>`. SMS consent is separate and needs an `admin` key: `PUT /v1/contacts/{id}/sms-consent` when the person has agreed. Details: [Contacts](/docs/contacts/contacts), [Consent and suppressions](/docs/contacts/consent-and-suppressions).

</Step>

<Step title="Create a sender per rep and connect their mailbox and number">

A sender is the rep the outreach comes from, addressed by your user id. Create them, then attach channels. Each channel is verified when saved: a wrong login is a `422` that names which login failed, so your "Connect your mailbox" form can show it.

<CodeGroup>

```bash title="curl"
curl -X PUT $SEQ/v1/senders/u_42 -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{ "name": "Max Rivera", "email": "max@acme.com", "timezone": "America/New_York", "signature_html": "<p>Max Rivera<br>Acme</p>" }'

# Email: any mailbox with SMTP and IMAP password login (Gmail and Google Workspace with an app password)
curl -X PUT $SEQ/v1/senders/u_42/channels/email -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{ "provider": "smtp",
        "smtp": { "host": "smtp.gmail.com", "port": 465, "secure": true, "user": "max@acme.com", "password": "app-password" },
        "imap": { "host": "imap.gmail.com", "port": 993, "secure": true, "user": "max@acme.com", "password": "app-password" } }'

# SMS and calls: the rep's Allo user id (usr-…) and a number the project's Allo key can see
curl -X PUT $SEQ/v1/senders/u_42/channels/sms -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{ "allo_user_id": "usr-…", "number": "+14155550123" }'

curl $SEQ/v1/senders/u_42/readiness -H "Authorization: Bearer $KEY"
```

```ts title="TypeScript"
await oseq.senders.upsert(user.id, { name: user.name, email: user.email, timezone: user.timezone, signature_html: user.signatureHtml });
await oseq.senders.setSmtp(user.id, { provider: 'smtp', smtp: form.smtp, imap: form.imap }); // 422 names the login that failed
await oseq.senders.setSms(user.id, { allo_user_id: picked.userId, number: picked.address });
const readiness = await oseq.senders.readiness(user.id); // { email: { ok, reason? }, sms: { ok, reason? }, task: { ok: true } }
```

</CodeGroup>

Passwords are encrypted on arrival and never returned; `GET /v1/senders/{id}/connections` shows hosts, ports and a `status` (`active`, `credentials_needed`, `restricted`, …) and nothing secret. SMS needs the project's Allo key first (`PUT /v1/project/providers/allo`); build the number picker from `GET /v1/project/providers/allo/numbers` and `.../users`. Details: [Senders](/docs/sending/senders), [Email via SMTP and IMAP](/docs/sending/email-smtp), [SMS and calls with Allo](/docs/sending/sms-and-calls-allo), [Call tasks](/docs/sending/call-tasks).

</Step>

<Step title="Register your webhook endpoint and verify every delivery">

One endpoint, subscribed to everything. The signing secret is in this response **once**: store it encrypted, keyed by the endpoint id.

<CodeGroup>

```bash title="curl"
curl -X POST $SEQ/v1/webhooks -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{ "url": "https://app.example.com/hooks/opensequence", "event_types": ["*"] }'
# → data: { id: "wep_…", url, event_types, status: "active", secret: "whsec_…", … }
```

```ts title="TypeScript"
const { id, secret } = await oseq.webhooks.create({ url: 'https://app.example.com/hooks/opensequence', event_types: ['*'] });
await db.settings.set('opensequence_webhook', { endpointId: id, secrets: [encrypt(secret)] });
```

</CodeGroup>

Deliveries follow Standard Webhooks: headers `webhook-id`, `webhook-timestamp` and `webhook-signature`, the signature being `v1,` plus base64 of HMAC-SHA256 over `${id}.${timestamp}.${raw body}` with the base64 secret after `whsec_`. Verify on the **raw** body, before parsing, with a 5-minute tolerance; keep a list of accepted secrets so a rotation is safe. Answer `2xx` within 10 seconds and do the work afterwards; the event `id` is your idempotency key, because a delivery can arrive twice.

```ts title="TypeScript (receiver)"
import { verifyWebhook, WebhookVerificationError } from '@opensequence/sdk';

app.post('/hooks/opensequence', express.raw({ type: 'application/json' }), async (req, res) => {
  let event;
  try {
    event = verifyWebhook({ headers: req.headers, body: req.body, secret: await currentSecrets() }); // string or [new, old]
  } catch (err) {
    if (err instanceof WebhookVerificationError) return res.status(401).end();
    throw err;
  }
  if (await db.events.seen(event.id)) return res.status(200).end();
  await queue.push(event); // handle out of band (next step)
  res.status(200).end();
});
```

Without the SDK, [Verifying signatures](/docs/webhooks/verifying) has the same check in Python and in shell, plus how to store and rotate the secret. [Receiving webhooks](/docs/webhooks/overview) has the payload and the catalogue; [Retries and recovery](/docs/webhooks/retries-and-recovery) covers failures and replay.

</Step>

<Step title="Create a sequence, validate it, publish it">

A sequence is a JSON document: nodes (`outreach`, `wait`, `condition`, `task`, `end`), transitions between them, `exit_on` rules and settings. Your product may ship a few and let users edit them in your own editor, or build them from a template. Validate before saving so your editor can show problems inline; publishing validates again and refuses on errors.

<CodeGroup>

```bash title="curl"
curl -X POST $SEQ/v1/sequences:validate -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d @definition.json
# → data: { valid, problems: [{ path, code, message, severity }] }

curl -X POST $SEQ/v1/sequences -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d "{ \"name\": \"Trial follow-up\", \"definition\": $(cat definition.json) }"
# → data: { sequence, version: { id: "ver_…", status: "draft", lockVersion, definition }, problems }

curl -X POST $SEQ/v1/sequences/seq_01J9…/versions/ver_01J9…/publish -H "Authorization: Bearer $KEY" -H "Content-Type: application/json"
```

```ts title="TypeScript"
const { problems } = await oseq.sequences.validate(definition);
const { sequence, version } = await oseq.sequences.create({ name: 'Trial follow-up', definition });
await oseq.sequences.versions.publish(sequence.id, version.id);
```

</CodeGroup>

A published version is immutable; to change it, copy it into a new draft (`POST .../versions`), edit under the optimistic lock (`PUT .../draft` with `lock_version`) and publish. People already enrolled finish on the version they started. The node types, their parameters and the condition fields are served by `GET /v1/schema` and `GET /v1/schema/fields`, so an editor reads them instead of hard-coding. Details: [Definition](/docs/sequences/definition), [Validation](/docs/sequences/validation), [Versions](/docs/sequences/versions), [Building a canvas](/docs/sequences/building-a-canvas).

</Step>

<Step title="Enroll">

Enroll by your ids: the contacts and the sender who sends. Preview first when a user is watching (it reports conflicts, exclusions and how many days the first touches will spread over, and writes nothing). A contact is in **one** active sequence per project: enrolling a batch with such a contact fails with `409 ALREADY_IN_SEQUENCE`, names the conflicts in `details`, and enrolls nobody.

<CodeGroup>

```bash title="curl"
curl -X POST "$SEQ/v1/sequences/seq_01J9…/enrollments:preview" -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{ "contacts": ["p_7", "p_8"], "sender": "u_42" }'

curl -X POST "$SEQ/v1/sequences/seq_01J9…/enrollments" -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{ "contacts": ["p_7", "p_8"], "sender": "u_42", "enrolled_by": "u_42", "enrolled_by_kind": "user" }'
# → data: { accepted: [{ contact_id, external_id, first_touch_at }], skipped: [{ contact_id, external_id, reason }],
#           capacity: { per_day, days_to_first_touches }, enrollments: [{ id: "enr_…", contact, status: "active", next_run_at }] }
```

```ts title="TypeScript"
import { OpenSequenceError } from '@opensequence/sdk';

const body = { contacts: selectedIds, sender: user.id, enrolled_by: user.id, enrolled_by_kind: 'user' as const };
const preview = await oseq.sequences.previewEnrollment(sequence.id, body);
try {
  const result = await oseq.sequences.enroll(sequence.id, body);
  await db.enrollments.insertMany(result.enrollments.map((e) => ({ id: e.id, contactId: e.contact, sequenceId: sequence.id })));
} catch (err) {
  if (err instanceof OpenSequenceError && err.code === 'ALREADY_IN_SEQUENCE') showConflicts(err.details); else throw err;
}
```

</CodeGroup>

Store the `enr_…` id on your side: webhooks and the journey are keyed by it. Contacts may be passed inline as `{ external_id, ...fields }` to upsert and enroll in one call. For "in a sequence" badges on your lists, `POST /v1/contacts:status` with up to 500 ids. Details: [Enrolling](/docs/contacts/enrolling).

</Step>

<Step title="Handle each event">

Every event is `{ id, type, project, occurred_at, data }`, `data` snake_case, with `data.enrollment` as a summary (`id`, `sequence`, `version`, `contact`, `sender`, `status`, `current_node_id`, `touch_count`, `replied_at`, `meeting_booked_at`, …). Resolve your records from the ids you stored: `enrollment.contact` is the `ctc_…` id, and `signal.received` also carries `data.contact.external_id`, your person id. What to write where:

| Event | What happened | What to write in your app |
|---|---|---|
| `enrollment.created` | the contact is in | status badge on the person: "in sequence X, step 1" |
| `run.done` | a step went out | an outbound activity on the person's timeline (channel, step, time). The subject and body are not in the payload: read the [journey](/docs/contacts/journey) and take the message whose `runId` is `run.id` |
| `run.skipped`, `run.failed`, `run.needs_review` | a step did not go out, with `reason` or `error` | an admin-visible note; `needs_review` and `failed` deserve a notification to the rep or an operator |
| `signal.received` with `kind: "reply"` | the contact answered (email or text) | an inbound activity, a notification to the sender, your CRM's stage or owner if that is your rule. `attribution` says which step earned it |
| `signal.received` with `kind: "meeting_booked"`, `call_connected`, `task_completed` | a positive outcome | the same, as a different activity type |
| `signal.received` with `kind: "bounce"`, `complaint`, `opt_out`, `contact_suppressed`, `ooo` | a negative or housekeeping signal | mark the address or number on the person; an out-of-office (`ooo`) is informational |
| `enrollment.exited` | the contact left, `exit_reason` one of `replied`, `meeting_booked`, `opt_out`, `bounced`, `suppressed`, `manual`, `deleted` | clear the badge, record the outcome |
| `enrollment.completed` | the sequence ran to its end with no reply | clear the badge, record "finished, no reply" |
| `enrollment.paused`, `enrollment.resumed` | by API, or because the sender was disabled | update the badge |
| `task.created` | a call or manual task is due for a sender | an item in that rep's task inbox, with `task.rendered` and `due_at`; complete it with `POST /v1/tasks/{id}/complete { outcome }` |
| `task.expired` | the task closed without the rep | remove it from the inbox (`task` is the full task when an exit cancelled it, only the id when its timer ran out) |
| `sender.channel_status` | a mailbox or number went `credentials_needed`, `restricted`, or back to `active` | a banner on the rep's settings page asking them to reconnect |
| `endpoint.disabled` | your receiver failed every delivery for three days | an alert to whoever runs the integration; fix it and call `POST /v1/webhooks/{id}/enable` to replay what was held |

The complete catalogue with every payload field is [Webhook events](/reference/webhook-events); ready-made handlers are in [Recipes](/docs/webhooks/recipes).

</Step>

<Step title="Report what the service cannot see">

The service only observes its own channels. A meeting booked in your calendar tool, a do-not-contact flag set in your app, or a reply that arrived somewhere else must be reported, or the sequence keeps going. One call per event, idempotent by your `id`:

<CodeGroup>

```bash title="curl"
curl -X POST $SEQ/v1/contacts/p_7/events -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{ "id": "booking_8812", "type": "meeting_booked", "occurred_at": "2026-10-20T15:00:00Z" }'
```

```ts title="TypeScript"
await oseq.contacts.reportEvent(person.id, { id: `booking_${booking.id}`, type: 'meeting_booked', occurred_at: booking.createdAt });
await oseq.contacts.reportEvent(person.id, { id: `dnc_${flag.id}`, type: 'suppressed', channel: 'all', reason: 'do_not_contact' });
```

</CodeGroup>

The four types are `meeting_booked`, `opt_out`, `suppressed` and `reply`; up to 500 at once with `POST /v1/contacts:events`. Details: [Contact events](/docs/contacts/events).

</Step>

<Step title="Pause, resume and exit">

Pause and resume keep the enrollment and its place in the sequence; exit ends it with `exit_reason: "manual"` and your label. Exiting needs an `admin` key. A selector form exits many at once.

<CodeGroup>

```bash title="curl"
curl -X POST $SEQ/v1/enrollments/enr_01J9…/pause  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d '{ "reason": "on holiday", "until": "2026-11-03T09:00:00Z" }'
curl -X POST $SEQ/v1/enrollments/enr_01J9…/resume -H "Authorization: Bearer $KEY" -H "Content-Type: application/json"
curl -X POST $SEQ/v1/enrollments/enr_01J9…/exit   -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d '{ "label": "deal closed" }'
curl -X POST $SEQ/v1/enrollments:exit -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d '{ "sequence": "seq_01J9…", "status": "active", "label": "campaign ended" }'
```

```ts title="TypeScript"
await oseq.enrollments.pause(enrollmentId, { reason: 'on holiday', until: '2026-11-03T09:00:00Z' });
await oseq.enrollments.resume(enrollmentId);
await oseq.enrollments.exit(enrollmentId, { label: 'deal closed' });
const { exited } = await oseq.enrollments.exitMany({ contact: person.id }); // or { sequence, status }
```

</CodeGroup>

When a rep leaves, `DELETE /v1/senders/{id}` disables them: their running enrollments pause and new ones are refused; exit them with the selector. The sender of a running enrollment cannot be changed; to move people to another rep, exit and enroll again (they restart from step one, and the re-enrollment rule applies). Details: [Lifecycle](/docs/contacts/lifecycle).

</Step>

</Steps>

## Admin UI you will build

OpenSequence ships no screens. Your product renders these in its own design system, from the reads below, and calls the actions. A single `admin` key covers every call on this list; each read is one request except where noted.

| Screen | What it shows | Reads | Actions |
|---|---|---|---|
| **Sequences** | every sequence with its status, versions and counts: running (`counts.active + paused + waiting_limit`), finished (`completed + exited`), plus replies and meetings | `GET /v1/sequences` (`oseq.sequences.list()`); `GET /v1/analytics/sequences` for `enrolled`, `replies`, `meetings` and rates of every sequence in one call | `POST /v1/sequences` (create), `PATCH /v1/sequences/{id}` (rename, pause, archive) |
| **One sequence** | its versions (`tag`, `status`, `publishedAt`), the flow drawn from the definition, per-step and per-channel results, exits by reason | `GET /v1/sequences/{id}`, `GET .../versions/{vid}` (`{ version, problems }`), `GET /v1/sequences/{id}/analytics/summary`, `.../nodes`, `.../channels`, `.../exits`; `GET /v1/schema` for the palette | `POST .../versions` (new draft), `PUT .../draft`, `POST .../publish`, `POST .../archive`, `POST /v1/sequences:validate` as the user edits |
| **People running** | who is in which sequence, at which step, with which sender; filters by sequence, status, sender, exit reason; bulk pause and exit | `GET /v1/enrollments?sequence=&status=&sender=&exit_reason=` (rows carry the enrollment and a `contact` summary with your `external_id`); `GET /v1/enrollments/{id}` for one person's journey | `POST /v1/enrollments/{id}/pause`, `.../resume`, `.../exit`; `POST /v1/enrollments:exit` for a selection; `POST /v1/sequences/{id}/enrollments` to add people |
| **Senders and inboxes** | each rep, their channels and the connection state of their mailbox and number, and whether they can run each kind of step | `GET /v1/senders` (`externalId` is your user id); `GET /v1/senders/{id}` adds `channels`, `connections` (`status`) and `readiness`; `GET /v1/senders/{id}/tasks` for their open tasks | `PUT /v1/senders/{id}`, `PUT .../channels/email`, `PUT .../channels/sms`, `PATCH .../channels/{channel}` (daily limits, pause a channel), `DELETE .../channels/{channel}`, `DELETE /v1/senders/{id}` |
| **Connections and health** | the service is up, queues are moving, provider keys are present, the webhook endpoint is healthy, recent deliveries | `GET /v1/engine/health`; `GET /v1/project` (settings, credential `status` per provider, never a secret); `GET /v1/webhooks` and `GET /v1/webhooks/{id}/deliveries` | `PUT /v1/project/providers/{provider}`, `PUT /v1/project/settings` (`sms_countries`, `send_window`, …), `PUT /v1/engine/flags/{key}` (kill switches), `POST /v1/webhooks/{id}/rotate-secret`, `.../enable`, `.../recover` |
| **A rep's task inbox** | calls and manual tasks due, with the rendered script and the contact | `GET /v1/tasks?sender=&status=open` or `task.created` events | `POST /v1/tasks/{id}/complete { outcome, note }`, `POST /v1/tasks/{id}/cancel` |

The exact fields of every response are on the endpoint's reference page and in [`openapi.json`](/openapi.json) under `components.schemas`; the SDK's types are generated from the same document.

## Before you ship

- Contacts are upserted wherever your app saves a person, so email, phone, country and attrs never lag.
- The webhook secret is stored encrypted, the handler verifies the raw body, answers `2xx` fast, and ignores an event `id` it has seen.
- Every event type in the table above writes somewhere, including `needs_review`, `sender.channel_status` and `endpoint.disabled`.
- Meetings and do-not-contact flags from your side are reported with `POST /v1/contacts/{id}/events`.
- Reps know before enrolling which steps they can run (`readiness`), and a disabled rep's people are exited or re-enrolled.
- Locally, the whole flow runs against mock providers in about ten minutes: [Quickstart](/docs/get-started/quickstart). The questions integrators ask next are in [Common questions](/docs/community/faq).
