---
title: "Queues"
description: "Choose between the postgres, redis and memory queue backends, and learn why a lost or duplicated queue message never loses or repeats work."
---

The worker moves work through four queues, and `SEQ_QUEUE` picks where they live. Keep the default unless the queue table itself becomes your bottleneck.

```bash
SEQ_QUEUE=postgres                                        # default: nothing else to run
SEQ_QUEUE=redis SEQ_REDIS_DSN=redis://redis.internal:6379 # higher throughput
SEQ_QUEUE=memory                                          # development and tests, one process
```

| Queue | Consumed by | Visibility timeout |
|---|---|---|
| `seq_email` | the email executor | 2 minutes |
| `seq_sms` | the SMS executor | 2 minutes |
| `seq_signals` | the signal processor (replies, bounces, bookings, calls) | 1 minute |
| `seq_webhooks` | outbound webhook deliveries | 30 seconds |

## Pick a backend

| `SEQ_QUEUE` | Extra infrastructure | What you get |
|---|---|---|
| `postgres` | none | Messages live in `seq.queue_messages`, read with `FOR UPDATE SKIP LOCKED`. An enqueue joins the transaction that records the work (a transactional outbox), so "run recorded" and "message queued" can never diverge. Dead letters go to `seq.queue_dead`. |
| `redis` | a Redis server with persistence on | More throughput for large installs. Keys are prefixed `oseq:`. An enqueue cannot join the database transaction, so the reaper re-enqueues anything recorded but never queued, and a message can arrive twice after a crash. |
| `memory` | none | One process only (`SEQ_ROLES=all`): an `api` and a `worker` in separate processes cannot share it. Lost on restart, which is safe because the planner and the reaper rebuild the work from the tables. |

The interface is the same for all three: `send`, `read` with a visibility timeout, `release`, `delete`, `archive` (dead letter) and `stats`. Everything above it behaves identically.

## Queues are hints

The database is the truth. A queue message only says "there may be work here". The consumer locks the row, checks its state, and does nothing when the work is already done or owned by someone else. That gives three guarantees:

- **A lost message costs a delay, never the work.** The `reap` job (every minute) re-enqueues runs recorded but not queued for 2 minutes, and deliveries whose next attempt is due. The `signals` job (every 30 seconds) re-enqueues signals left unprocessed for 2 minutes.
- **A duplicated message costs nothing.** The second consumer finds the run finished or owned, or the delivery busy, and drops it.
- **Switching backends, flushing Redis, or scaling the worker to zero loses no work.**

## Retries

A message a consumer reads stays invisible for its visibility timeout. If the consumer dies, the message reappears when the timeout ends.

| Message | On failure |
|---|---|
| email step | released with backoff (1 minute, doubling, capped at 30 minutes, plus jitter). After 5 reads the run fails |
| SMS step | never retried blindly: an unknown outcome marks the run `needs_review` (see [Observability](/docs/self-hosting/observability)) |
| signal | released with a growing delay (1 minute per read, up to 10 minutes). Archived after 10 reads |
| delivery | released with the delivery's own backoff schedule. See [Retries and recovery](/docs/webhooks/retries-and-recovery) |

The reaper also releases planner claims older than 10 minutes and fails runs stuck in `running` for 2 hours.

## Watch them

```bash
curl $SEQ/v1/admin/engine/health -H "Authorization: Bearer $SEQ_ADMIN_TOKEN"
# "queues": [{ "queue": "seq_email", "depth": 3, "oldestMs": 1200 }, …]
```

`depth` counts every message in the queue, including those in flight or delayed for a retry. `oldestMs` is how long the oldest ready message has been waiting. An empty queue is not listed. A depth that keeps growing while the worker is up, or an `oldestMs` that keeps rising, means the worker is behind: add a replica or raise `SEQ_CONCURRENCY`. See [Scaling](/docs/self-hosting/scaling).
